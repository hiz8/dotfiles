# ライブラリ更新内容の調査

## 概要

指定されたライブラリについて、**現在プロジェクトで使用中のバージョン**と**指定バージョン**の間の更新内容を調査し、決められた 4 観点で日本語のレポートを作成します。

**基本原則:** 調査の起点は、現在プロジェクトで使用中のバージョンです。変更は一次情報（GitHub Release・CHANGELOG）を根拠にします。

## 使うとき

- 依存ライブラリを特定のバージョン、または最新版へ更新する前の事前調査を頼まれたとき
- 依存の更新・アップグレードの前に、互換性や破壊的変更を確かめたいとき

## 手順

### 0. 対象を読み取る

- ユーザーの依頼から、ライブラリ名（npm パッケージ名。例: `react`, `@tanstack/react-router`）とターゲットバージョン（例: `19.2.0`, `1.180.0`）を読み取ります。`react 19.2.0` のように 2 語だけ渡された場合は、1 語目をライブラリ名、2 語目をターゲットバージョンとして扱います。
- ターゲットバージョンが無ければ、最新安定版を対象にします。最新安定版は `npm view <library> dist-tags` の `latest` を採用し、`beta` / `rc` / `next` / `canary` / `experimental` などのプレリリースタグは選びません（`versions` 配列の末尾はプレリリースを含みうるため使いません）。
- ライブラリ名が読み取れなければ、何を調査すればよいかユーザーに尋ねてから進めます。

### 1. 現在使用中のバージョンを特定する

1. リポジトリ内の `package.json` を探します（ルートおよびワークスペース）。`node_modules` 配下を除いて、`**/package.json` に一致するファイルを探してください。
2. 対象ライブラリが `dependencies` / `devDependencies` / `peerDependencies` のどれに、どの範囲（`^4.1.0` など）で記載されているかを確認します。
3. 実際にインストールされている確定バージョンを `npm ls <library> --depth=0`（取得できなければ lockfile）で確認します。範囲表記と確定バージョンが異なる場合は、確定バージョンを「現在のバージョン」として扱います。
4. 対象ライブラリが依存に存在しない場合は、その旨を報告し、ユーザーに意図を確認します（新規導入の検討か、パッケージ名の誤りか）。このケースでは手順 2 以降に進まず、確認を提示した時点で停止してください。いずれかの意図（新規導入 / 名前誤り）を勝手に仮定して調査を続行してはいけません。

### 2. パッケージとリリースノートの所在を特定する

1. `npm view <library> repository.url` と `npm view <library> homepage` で、ソースリポジトリ（多くは GitHub）を特定します。
2. `npm view <library> repository.directory` を確認し、モノレポ内のパッケージかどうかを判断します（タグ名が `pkg@1.2.3` 形式になることがあります）。
3. `npm view <library> versions --json` で、現在バージョンとターゲットバージョンの間に存在する全リリースを把握します。semver でメジャー跨ぎか（破壊的変更が入りやすい）を判断します。

### 3. リリースノートを収集する

現在バージョン（排他）からターゲットバージョン（包含）までの全リリースを対象に、変更内容を集めます。以下を優先順に試してください。

1. **GitHub Releases**: `https://github.com/<owner>/<repo>/releases` を取得します。タグ命名の揺れ（`v1.2.3` / `1.2.3` / `pkg@1.2.3`）に注意してください。
2. **CHANGELOG**: `https://raw.githubusercontent.com/<owner>/<repo>/<default-branch>/CHANGELOG.md` などを取得します。
3. **移行ガイド**: メジャー跨ぎの場合は、公式の migration / upgrade guide を Web 検索とページの取得で探します。
4. 上記で不足する場合は Web 検索で補います。ライブラリのドキュメントや GitHub を参照する MCP ツールが利用可能な環境なら、補助的に活用して構いません（必須ではありません）。

各変更には、それが導入されたバージョンと出典（リリースページ等）を必ず紐付けてください。あわせて、収集した変更を「新機能の追加」と「それ以外（バグ修正・パフォーマンス改善・内部リファクタ・ドキュメント変更・依存更新など）」に分類しておきます。

**出典の優先順位（一次情報の裁定）**: GitHub Release タグ本文・CHANGELOG を一次情報とします。Web 検索の結果や、要約を介して取得したページは二次情報として扱い、一次情報と一致する項目のみ採用します。一次情報に記載が無い変更は、検索で出てきてもレポートに載せてはいけません。一次情報と二次情報が食い違う場合は、一次情報を優先します。一次情報自体が取得できない場合は、その旨を明記したうえで、二次情報を「未確認」と注記して扱います。

### 4. プロジェクトへの影響を分析する（コード使用箇所まで）

リリースノートから抽出した「新機能」「破壊的変更」のそれぞれについて、プロジェクトの実コードを調べて影響を判定します。

- 破壊的変更が触れている API・関数・設定キー・import パス・型などを、プロジェクト全体（`node_modules` を除く）から検索します。
- 該当する使用箇所が見つかった破壊的変更を「影響あり」と判定し、`ファイルパス:行番号` を添えて具体的に示します。
- 新機能のうち、現在の手書き実装・回避策・非推奨 API の利用を置き換えられそうなものを「有用」と判定し、根拠となるコード箇所を示します。
- 判定は確証のあるものを優先します。推測が混じる場合は、その旨を明示してください。

### 5. レポートを作成する

以下の 4 セクション構成で、日本語のレポートを簡潔に出力します。各項目は要点を 1〜2 行にまとめ、導入バージョンと出典を添えてください。冗長な前置きや説明は省きます。

**「なし」最小記法ルール（全セクション共通）**: 4 つのセクションのいずれも、該当が無ければ本文を `なし` の一語だけにします。理由・根拠・出典・「破壊的変更が無いことの説明」などの補足を**一切添えてはいけません**（セクション 3・4 のような重要セクションであっても同じです）。補足を書いてよいのは、レポート末尾の総括の一文のみです。

```
## <library> の更新調査: <現在バージョン> → <ターゲットバージョン>

対象リリース: <跨ぐバージョンの一覧 / メジャー跨ぎの有無>

### 1. 主な追加機能
- <項目>

### 2. 現在のプロジェクトに有用な追加機能
- <項目>

### 3. 破壊的変更
- <項目>

### 4. 現在のプロジェクトに影響がある破壊的変更
- <項目>
```

**各セクションに書くもの:**

1. **主な追加機能**: バージョン間で**新しく追加された機能のみ**を、導入バージョンと出典付きで簡潔に列挙します。バグ修正・パフォーマンス改善・内部リファクタ・ドキュメント変更・依存更新などは含めません。
2. **現在のプロジェクトに有用な追加機能**: 1 のうち、このプロジェクトのコードに照らして役立つものを、理由と該当コード箇所を添えて書きます。該当が無ければ「なし」とだけ書き、理由や補足説明は一切添えないでください。
   - ここに載せてよいのは **1 に列挙した「追加機能」だけ**です。バグ修正・小改善は、プロジェクトのコードに接点があっても載せません（それらは自動適用され、対応不要なためです）。接点を見つけても「追加機能」でなければ「なし」と書きます。無理に該当を作ってはいけません。
3. **破壊的変更**: バージョン間の破壊的変更を、導入バージョンと出典付きで列挙します。該当が無ければ「なし」とだけ書き、理由や補足説明は一切添えないでください。
   - ここでの「破壊的変更」は、既存のコードが**そのままでは動かなくなる**変更（API の削除・改名・シグネチャ変更・デフォルト挙動の非互換変更など）を指します。**deprecation（非推奨化）は、旧 API が動作し続ける限りこのセクションに含めてはいけません**。後継 API があれば、セクション 1 で新機能として扱います。
4. **現在のプロジェクトに影響がある破壊的変更**: 3 のうち、このプロジェクトのコードに実際の影響があるものを、該当する `ファイル:行` と必要な対応を添えて書きます。該当が無ければ「なし」とだけ書き、理由や補足説明は一切添えないでください。

最後に、3〜4 で重大な影響が見つかった場合は、対応の要否・規模を一文で総括します。

## よくある間違い

- **最新版同士の差分を調べてしまう** → 調査の起点は、あくまで「現在プロジェクトで使用中のバージョン」です。
- **区間の一部のリリースだけを見てしまう** → バージョン区間に複数のメジャー / マイナーが含まれる場合は、その全区間の変更を累積して扱います。
- **見つからないリリースノートを推測で埋めてしまう** → リリースノートが見つからない・特定できない場合は、推測で埋めず「確認できなかった」と明記します。
- **取得できなかった範囲を黙って省いてしまう** → ネットワーク取得が制限されている環境では、取得できた範囲を明示したうえで報告します。
- **列挙を長くしすぎる** → レポートは簡潔さを優先します。各項目は要点を短くまとめ、列挙が長くなる場合は影響の大きいものに絞ります。
