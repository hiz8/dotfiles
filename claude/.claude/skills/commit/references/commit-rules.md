# コミットメッセージ規約

SKILL.md とは分離し、ルールだけを参照できるようにしています。各ルールの末尾には検証区分を付けています。

- [機械] … `[SKILL_DIR]/scripts/check-commit-message.mjs` が自動検証します。
- [自己] … 機械では検証できないため、人やエージェントが自己チェックします。

## テンプレート

```
<コミット種別>: <コミットタイトル> <Issue番号>

<コミット内容>
```

リポジトリ別拡張がある場合、1 行目は `<接頭辞><コミットタイトル> <Issue番号>` になります。

## ルール

### コミット種別

- リポジトリに拡張（git config `commit-skill.extensionDir` で指定したディレクトリ）が
  ある場合は、この節の代わりにその接頭辞ガイドに従ってください。拡張の有無は、手順書の
  とおり `--show-rules` で確認します。[機械]
  - 設定例: `git config --local commit-skill.extensionDir <パス>`。相対パスはメインの
    作業ツリーのルートから解決され、全 worktree で共有されます。ディレクトリには
    `config.json` と接頭辞ガイドを置きます。
  - 拡張の `subjectPrefix` は `u` フラグ付きの正規表現として解釈され、subject の先頭で
    判定されます。`\:` のような不要なエスケープは設定エラーになります。
- 先頭に、コミットの種別を示す文字列をコロンと半角スペース区切りで記載してください。[機械]
  - feat
  - fix
  - docs
  - refactor
  - test
  - chore
- 種別の選び方（迷ったとき）。[自己]
  - feat … 利用者から見た新しい挙動・機能の追加
  - fix … 既存の不正・不足な挙動の是正（バグ修正）
  - refactor … 外部から見た挙動を変えない内部整理
  - docs … ドキュメントのみの変更
  - test … テストのみの追加・修正
  - chore … ビルド・依存・設定など上記以外
  - 性能改善は、挙動が変わるなら feat、変わらない整理なら refactor に寄せます。
    `perf` など上記リスト外の種別は使ってはいけません。

### コミットタイトル

- タイトルを空にしてはいけません（空白だけも不可）。[機械]
- タイトル（種別・接頭辞と Issue 番号を除く）は 50 文字を目安に簡潔に記述してください。
  超えると機械チェックが注意を出しますが、意味を損なう場合は超えてもかまいません。[機械]
- subject の 1 行全体（種別・接頭辞と Issue 番号を含む）は 72 文字以内にしてください。
  GitHub で 72 文字を超える 1 行目が省略して表示されることがあるためです。[機械]
- 文末は「体言止め（例：〜の修正）」または「現在形（例：〜を変更）」とし、過去形や
  「です・ます」調は禁止します。[自己]

### Issue番号

- コミットに直接関連する Issue の番号があれば、それを記載してください。[自己]
  - 記法は subject 末尾の ` #42` を既定とします（body 先頭の `#42 の対応` も可）。
  - 関連 Issue がなければ省略します（プレースホルダを残さないでください）。

### コミット内容

- コミット内容は全体をリスト形式で記述してください。Why を含め、地の文（リストでない段落）を
  書いてはいけません。説明が長い場合もリスト項目の折り返しで表現し、段落にしないでください。[自己]
- 1行の表示幅は半角80桁以内にしてください。全角文字は2桁、半角文字は1桁として数えます。[機械]
- 改行は「80桁を超える直前」で行い、80桁ぎりぎりまで詰めてください。[機械]
- 80桁以内でも不必要に早い改行は禁止します。原則として、各行は表示幅70〜80桁を目安に
  詰めます。[機械]
- ただし、次の行は70桁未満でも許容します。[機械]
  - 文の終端で自然に終了する行
  - 次行に続けると80桁を超える行
  - URL・コマンド・識別子など分割不適切な文字列を含む行
  - 次行が新しいリスト項目（行頭が `-` `*` `+` または `数字.`）として始まる行。
    その行は折り返しの継続行ではないため、短くても詰め直す必要はありません
- 改行位置は単語・助詞・読点の区切りを優先し、意味の切れ目を保ってください。[自己]
- コミット前に、全行について全角2桁/半角1桁の表示幅で自己チェックしてください。[機械]
- 原則として、Why（技術的な原因・背景）を先に述べ、What（具体的な変更点）を続けます。
  ただし、コードを見れば What が理解できる場合は What の記載を省略します。[自己]
  - diff を見れば分かる詳細の列挙で冗長にしてはいけません。変更した個々のファイル名・
    コンポーネント名・シンボル名を網羅列挙したり、commit hash などの識別子を literal で
    書き写したりしないでください（いずれも diff から辿れます）。「何を・なぜ変えたか」が
    伝わる粒度に留め、コードの再掲にすぎない下位リストは足さないでください。
  - Why には「技術的な原因」や「仕様上の不備」を記載してください。「レビューで指摘された
    ため」や「修正依頼の対応」といった、修正のきっかけ（プロセス）は記載しないでください。
- コミット内容は変更の要点だけに絞ってください。詳しい経緯や仕組みの解説は PR の「内容」
  セクションに任せ、コミットには書きません。[自己]
  - 次のような補足は書かないでください。
    - 再現条件の詳細や、起きない条件との対比（例: 「ドラッグでは起きない」）
    - 原因に至る仕組みの段階的な解説や、具体的な数値・計算の内訳
    - 既存の挙動を残した理由や、適用範囲・対象外・今後の調査予定の説明
  - ライブラリのバージョンなど、変更の理解に必須でないメタ情報は書かないでください。
    依存の更新そのものがコミットの主題である場合など、必須な場合は書いてかまいません。
  - 迷ったら「この項目がなくても、何を・なぜ変えたかは伝わるか」で判断し、伝わるなら
    削ります。
- 不具合修正のコミットは、事象・原因・対応の順に短くまとめてください。[自己]
  - 最初の項目で修正対象の事象を述べ、「〜問題の対応」または「〜事象の対応」で結びます。
  - 次の項目で原因を「〜が原因」の形で 1 文にまとめます。
  - 対応内容は原因の項目の下にネストし、「〜する形で対応」のように結びます。対応内容が
    コードを見れば分かる場合は省略します。
- 特定の Issue に関するコミットであれば、先頭に `<Issue番号> の対応` と記載してください。[自己]
- 文末は「体言止め（例：〜の修正）」または「現在形（例：〜を変更）」とし、過去形や
  「です・ます」調は禁止します。[自己]
  - Why で既存の不備を説明する場合も過去形にしないでください。問題は過去の出来事ではなく、現在も
    続く状態として現在形・体言止めで書きます（「〜していた」→「〜している」「〜が生じる」、
    「〜になっていた」→「〜になっている」）。
- Markdown記法による装飾（`**` による太字など）は禁止します。すべてプレーンテキストで
  記述してください。[機械]
- Markdownの装飾（太字等）や、強調記号（`【】`, `[]`等）の使用は禁止します。[機械]
  （`**` `【` `】` は機械検証します。`[]` は `[CI]` 等の正当用例があるため自己チェックです）
  拡張の接頭辞として subject の先頭に付ける `[...]` は、この禁止の対象外です。
- 項目のグルーピングは、見出し記号を使わず「リストのネスト（インデント）」で表現して
  ください。[自己]
- テストの実行結果（「全テスト通過」「○件成功」など）や、ビルドのステータスの記載は
  禁止します。[自己]
- `Co-Authored-By:` トレーラーの記載は禁止します。一部のモデルがコミットメッセージ末尾に
  自動付与することがあるため、含まれていれば削除してください。[機械]

### サンプル

```
#### 良い例（技術的な理由が書かれている）
- #123 の対応
- イベントフォーム画面で発生したランタイムエラーの対応
  * 引数の型が想定と異なっていたため、正しい型定義に変更

#### 悪い例（プロセスの経緯が書かれている）
- #123 の対応
- レビュー指摘の対応
  * 指摘された箇所の修正

#### 良い例（不具合修正を事象・原因・対応の順に要点だけで書いている）
- 一覧をマウスホイールで下へスクロールすると、スクロール位置が先頭へ押し戻される
  事象の対応
- 行の高さについて実際の表示とグリッドの計算が食い違うことが原因
  * wheel イベントをグリッドのハンドラに届かせず、ブラウザ標準のスクロールに
    任せる形で対応

#### 悪い例（補足やメタ情報が多く、PR に書くべき内容まで含んでいる）
- 一覧をマウスホイールで下へスクロールすると、位置が先頭へ押し戻される。
  スクロールバーのドラッグでは起きない
- 原因は、行の高さについて実際の表示と grid-lib（4.7.1）の計算が食い違うこと
  * 実際の行は 34px 以上になる一方、grid-lib は全行を 30px として計算する
- wheel イベントをグリッドのハンドラに届かせない属性ディレクティブを追加
- ヘッダー上の wheel は従来どおりグリッドに渡す。既存の挙動を保つため
- 適用先は一覧画面だけ。他の画面は別途調査して判断する

#### 悪い例（地の文で始まり、diff で分かる詳細を再掲していて冗長）
暫定対応として追加していた余白は、根本対応が機能したため不要となった。
防御的に維持していた余白を削除する。

- @example/ui を対応 commit hash 7ebbeb8... へ更新
- フォームの余白指定を削除
  * ComponentA の Stack から paddingBottom を除去
  * ComponentB の Stack から paddingBottom を除去
- 上記に伴うスナップショットテストの更新

#### 良い例（全体をリスト化し、diff で分かる詳細を省いている）
- 暫定対応として追加している余白は、根本対応が意図通り機能しているため不要。
  よって防御的に維持している余白を削除する
- @example/ui を対応 commit hash へ更新
- フォームの余白指定を削除
- 上記に伴うスナップショットテストの更新
```

## コミット実行方法

- 関連ファイルを個別に `git add` してください（`git add -A` や `git add .` は使わないでください）。
- コミットメッセージは一時ファイルに書き出し、`git commit -F <ファイル>` で渡してください。
  `git commit -m` の引数に直接文字列を渡すと、改行が `\n` リテラルとして埋め込まれる
  問題があるため使ってはいけません。

```bash
git commit -F <message-file>
```
