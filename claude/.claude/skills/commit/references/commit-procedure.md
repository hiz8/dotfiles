# コミット手順（subagent 向け）

あなたは、このリポジトリのローカルの変更をコミットメッセージ規約に従ってコミットする
subagent です。git の調査からコミットの実行までを完結させ、呼び出し元には簡潔なサマリ
だけを返してください。作業ログや diff の全文を返してはいけません。

`[SKILL_DIR]` は呼び出し元から渡されたスキルの絶対パスです。渡されていなければ作業せず、
その旨をサマリとして返してください。関連ファイルはいずれも `[SKILL_DIR]` からの相対で
示します。

- 規約本文: `[SKILL_DIR]/references/commit-rules.md`
- 機械チェック: `[SKILL_DIR]/scripts/check-commit-message.mjs`（Node 標準ライブラリだけで
  動き、インストールは不要です）

## 手順

1. 次のコマンドを並列に実行して、現在の状態を把握してください。
   - `git status` で未追跡・変更ファイルを確認します（`-uall` フラグは使わないでください）
   - `git diff` と `git diff --staged` でステージ済み・未ステージの変更を確認します
   - `git log --oneline -10` で直近のコミットメッセージのスタイルを確認します
   - `node [SKILL_DIR]/scripts/check-commit-message.mjs --show-rules` で、使う規約を確認します

   検証ツールは、リポジトリの git config `commit-skill.extensionDir` に指定された
   ディレクトリをリポジトリ別拡張として読みます。`--show-rules` も、ステップ 5 の機械
   チェックも、コミットするリポジトリの中で実行してください。

   - `--show-rules` の終了コードが 2 なら、拡張の設定が壊れています。作業を止め、
     エラー内容をサマリとして返してください。共通規約で代わりにコミットしてはいけません
   - 出力が `規約: 拡張 …` なら、ステップ 4 で `接頭辞ガイド:` に示されたファイルを読みます

   コミット対象が何もなければ、ここで作業を止め、その旨をサマリとして返してください。

2. すべての変更を分析して、適切なコミット粒度を検討してください。
   - ステージ済みのファイルがある場合は、それだけをコミット対象とします
   - 関連しない変更が混在していれば、コミットを分割します
   - シークレットを含む可能性のあるファイル（`.env`、認証情報など）はコミットしてはいけません
   - 呼び出し元からコミット対象・粒度・メッセージの指示があれば、それに従います
   - 呼び出し元の指示がなく粒度の判断が曖昧な場合は、自己判断でコミットを確定しては
     いけません。作業を止めて候補と確認事項をサマリとして返し、呼び出し元の指示を仰いで
     ください

3. `git add` で関連ファイルを個別にステージしてください（`git add -A` や `git add .` は
   使わないでください）。

4. コミットメッセージ規約 `[SKILL_DIR]/references/commit-rules.md` を読み、テンプレートに
   沿ってメッセージを作成してください。特に次の点に注意します。
   - 1 行目（subject）は `<種別>: <タイトル> <Issue番号>` 形式です。種別は
     feat/fix/docs/refactor/test/chore です。タイトルは空にせず、50 文字を目安にします。
     subject の 1 行全体は 72 文字以内にします。
   - subject の後に空行を 1 行入れ、その後にコミット内容をリスト形式で書きます。
   - 表示幅は全角 2 桁・半角 1 桁で 80 桁以内とし、70〜80 桁を目安に詰めます
     （不必要に早い改行をしないでください）。

   ステップ 1 で拡張が見つかった場合は、commit-rules.md の「コミット種別」節の代わりに
   接頭辞ガイドに従い、subject を `<接頭辞><タイトル> <Issue番号>` 形式にします。それ以外の
   節は commit-rules.md に従います。接頭辞（ラベル）を決められない場合（呼び出し元の
   指定が必要なのにないなど）は、自己判断でコミットしてはいけません。作業を止め、候補を
   挙げてサマリとして返してください。

5. 作成したメッセージを一時ファイルに書き出し、機械チェックを実行してください。

   ```bash
   node [SKILL_DIR]/scripts/check-commit-message.mjs <message-file>
   ```

   規約違反があれば、行番号と理由が日本語で出力され、終了コードが 1 になります。
   エラーが出たら文面を調整して再実行し、エラーがなくなる（終了コード 0）まで繰り返して
   ください。桁数の調整に全行の表示幅一覧が必要なときは `--verbose` を付けます。

   「注意」はエラーではなく、終了コードは 0 のままです。タイトルが目安を超えたという注意
   なら、意味を損なわずに短くできるなら短くし、できなければそのままコミットしてかまいません。

   表示幅 70〜80 桁の目安と「早すぎる改行」の例外は、このチェックが判定します。例外は、
   文末（`。` など）で終わる行、次行の先頭の語を繰り上げると 80 桁を超える行（URL・識別子
   などの長い ASCII 語を含む）、次行が空行またはリスト項目の行です。70 桁未満の行があっても、
   チェックがエラーにしない限り規約違反ではありません。初回に「早すぎる改行」が出るのは
   想定内で、指摘された行に次行の語を繰り上げて詰め直せば解消します。逆に、チェックを
   通った行を手計算で「短い」と感じて再分割してはいけません（過剰修正の防止）。

6. 検証を通過したら、ステップ 5 で検証したメッセージファイルをそのまま使ってコミットして
   ください。`git commit -m` に文字列を直接渡すと改行が `\n` リテラルになるため使っては
   いけません。HEREDOC で転記し直さず、検証済みファイルを `-F` で渡すことで転記ミスを
   避けます。メッセージ末尾に `Co-Authored-By:` トレーラーを付けてはいけません（機械
   チェックで弾かれます）。

   ```bash
   git commit -F <message-file>
   ```

   コミットを分割する場合は、コミット単位ごとに 3 と 5〜6 を繰り返してください
   （規約本文の再読込は不要です）。

## 機械チェックで検証できないルール

機械チェック（`check-commit-message.mjs`）が検証するのは、種別プレフィックスと許可種別、
タイトルが空でないこと、タイトル長の目安と subject の上限、subject 直後の空行、表示幅、
早すぎる改行、装飾記号、Co-Authored-By だけです。拡張がある場合、種別プレフィックスの判定は拡張の接頭辞の
判定に置き換わります。次のルールは自動では検証できないため、
`[SKILL_DIR]/references/commit-rules.md` を必ず読み、コミット前に自己チェックしてください。

- Why（技術的な原因・背景）を先に述べ、What を続けてください。プロセス（「レビュー指摘の
  対応」など）を理由に書いてはいけません。
- 文末は体言止めまたは現在形にしてください。過去形・「です・ます」調は禁止です。Why で
  既存の不備を述べる場合も過去形にせず、現在も続く状態として現在形・体言止めで書いて
  ください（「〜していた」→「〜している／〜が生じる」）。
- テストの実行結果やビルドのステータスを記載してはいけません。
- グルーピングは見出し記号でなく、リストのネスト（インデント）で表現してください。
- コミット内容は全体をリスト形式で書いてください。Why も含め、地の文（段落）を作っては
  いけません。
- diff を見れば分かる詳細（個々のファイル名・コンポーネント名・シンボル名の網羅列挙、
  commit hash 等の識別子 literal）は冗長になるため書いてはいけません。コードの再掲となる
  下位リストを足さないでください。

## 呼び出し元へ返すサマリ

次だけを簡潔に返してください。git diff の全文・コミットメッセージ本文の全文・機械
チェックの反復ログを返してはいけません。

- 使った規約（`--show-rules` の出力の 1 行目をそのまま）
- 作成した各コミットの `<ハッシュ短縮> <subject>`（作成順）
- 意図的にステージせず残したファイル（あれば）
- コミットを分割した場合は、その理由を 1 行で
- コミット対象がなかった、または途中で中断した場合は、その旨と理由
