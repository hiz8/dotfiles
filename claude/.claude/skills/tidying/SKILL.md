# Tidying（Tidy First）

## 概要

整理（tidying）は、振る舞いを変えずにコードの構造だけを変える、小さな変更です。

**基本原則:** 構造の変更と振る舞いの変更を分けます。整理は 1 種類ずつ行い、そのたびにテストを通してコミットします。

**ルールの文言に違反することは、ルールの精神に違反することです。**

**開始時に宣言する:** 「tidying スキルを使って整理します。」

## 使うとき

- **場面 1（Tidy First）:** 機能追加やバグ修正の前に、これから手を加えるファイルを整理するよう頼まれたとき。整理だけのブランチ・PR にし、続く振る舞いの変更とは混ぜません
- **場面 2:** 開発の合間などに、整理だけを頼まれたとき

**使わないとき:** 振る舞いの変更だけを頼まれたとき。頼まれていない整理を自分の判断で始めてはいけません。

## 鉄則

```
整理のコミットに振る舞いの変更を入れてはいけません。
1 つのコミットには 1 種類の整理だけを入れ、コミットのたびにテストを通さなければなりません。
整理する振る舞いをテストが確かめていないなら、整理より先にテストを書いてコミットしなければなりません。
```

## 手順

1. **対象を決める。** 場面 1 では、これから手を加えるファイルです。依頼から特定できなければ、推測で広げずにユーザーに確かめてください。場面 2 では、依頼された範囲です。範囲の外で見つけたものは、手を付けずに報告に回します
2. **整理専用のブランチで作業する。** 現在のブランチが main / master なら、新しく切ってください
3. **テストを実行し、グリーンであることを確かめる。** プロジェクトのテストコマンドを特定して実行します
4. **振る舞いを固定する。** テストがない場合や、これから整理する部分の振る舞い（境界、空の入力、分岐）をテストが確かめていない場合は、今の振る舞いをそのまま期待値にした characterization test を書きます。グリーンを確かめ、**整理より先に、テストだけのコミット**にしてください
5. **候補の一覧を作る。** [tidyings.md](tidyings.md) を読み、「パターン × 箇所」を 1 行ずつ書き出します。1 行が 1 コミットになります（下の「1 コミットの単位」）。一覧をユーザーに見せたら止まり、了承を得てから始めます。ユーザー自身が「確認は不要」「返事ができない」と伝えている場合に限り、止まらずに一覧を最後の報告に含めて進めます。期限が近いことは、止まらない理由になりません
6. **一覧の 1 行ずつ、適用 → テスト → コミットを繰り返す。** テストが落ちたら、テストを直さずにその整理を取り消し（`git restore`）、次の行に進むか報告に回します
7. **報告する。** コミットの一覧、整理中に見つけたが手を付けなかったもの（バグ、コメントとコードの食い違い、範囲外の問題）、一覧から外した候補とその理由を書きます
8. **仕上げる。** 完了と言う前に superpowers:verification-before-completion に従います。push と PR の作成はこのスキルでは行わず、superpowers:finishing-a-development-branch に任せます。場面 1 では、続く機能追加やバグ修正は別のブランチで行います。整理ブランチから切るか、マージ後に切るかはユーザーに確かめてください

## 1 コミットの単位

1 コミット = 候補の一覧の 1 行 = [tidyings.md](tidyings.md) の 1 パターンです。

- 同じパターンを同じファイルの複数の箇所に適用するのは、1 つのコミットにしてかまいません
- 関数やファイルは単位ではありません。たとえば 1 つの関数に対して Guard Clause、ヘルパーの抽出、説明用の定数を行うなら、コミットは 3 つです
- テストの追加は、整理とは別のコミットにします
- コミットメッセージにはパターン名を入れます（例: `refactor: calcTotal に Guard Clause を導入`）。メッセージに 2 つ以上のパターンを並べたくなったら、コミットを分けてください

## 自己正当化の表

| 言い訳 | 現実 |
|--------|------|
| 「テストがないので、整理の前後に同じ入力を与えて結果を比べた」 | その比較はリポジトリに残らず、レビュアーも次の作業者も再実行できません。同じ入力と期待値を characterization test にしてコミットしてください |
| 「急いでいるので、テストを書く時間はない」 | テストは整理の前の 1 コミットです。時間がないなら、テストを省くのではなく、整理の候補を減らしてください |
| 「同じ関数の整理なので、1 コミットにまとめる」 | 関数はコミットの単位ではありません。パターンごとに分けます |
| 「時間がないので、1 コミットにまとめる」 | まとめると、振る舞いが変わっていないことをレビューで確かめにくくなります。分けるコストはコミット 1 回分です |
| 「テストは最後に 1 回通せば十分」 | どの整理で壊れたのか分からなくなります。コミットのたびに実行します |
| 「時間がないので、了承を待たずに一覧を報告に含めて進める」「ユーザーはすぐには返事できないだろう」 | 確認できないかどうかは、ユーザーが自分でそう伝えたときにだけ分かります。伝えられていなければ、一覧を見せて止まってください。了承を待つ時間は、間違った整理をやり直す時間より短くて済みます |
| 「テストの追加も整理の一部なので、同じコミットに入れる」 | テストは整理の前に、グリーンを確かめて別のコミットにします。同じコミットでは、テストが元の振る舞いを固定していることを確かめられません |

## Red Flags — 止まってやり直してください

- テストがないまま、整理の差分を書き始めた
- 振る舞いの比較スクリプトを書いて、コミットせずに消そうとしている
- 1 つのコミットメッセージに、複数のパターン（「〜を平坦化し、〜を分離」）が並んでいる
- 候補の一覧を作らずに、ファイル全体を書き直している
- ユーザーが伝えていないのに「返事はもらえない」と決めて、一覧を見せずに始めた

**どれかに当てはまったら、コミット前の変更を取り消し、手順 4 か手順 5 からやり直してください。**

## よくある誤り

- **Guard Clause で外側の `if` を消すだけにする:** 条件を満たさないときの結果が変わることがあります。元の結果を先頭で返してください（[tidyings.md](tidyings.md) の例を参照）
- **コメントとコードの食い違いを「冗長なコメントの削除」で片付ける:** どちらが正しいかは振る舞いの判断です。整理の対象から外して報告します
- **名前の根拠がないまま定数に名前を付ける:** 業務上の意味をコードやテストから読み取れない場合は、候補から外して報告します
