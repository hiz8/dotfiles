## ルール

**関連するスキルや依頼されたスキルは、いかなる応答や行動よりも前に呼び出してください** — 確認のための質問、コードベースの探索、ファイルの確認も含みます。状況に合わないと分かったら、そのスキルを使う必要はありません。

**plan mode に入る前に:** まだブレインストーミングしていなければ、先に brainstorming スキルを呼び出してください。

その後「[purpose] のために [skill] を使います」と宣言し、スキルに正確に従ってください。スキルにチェックリストがあれば、項目ごとに todo を作ってください。

## スキルの優先順位

複数のスキルが当てはまるときは、プロセススキルを先に使います — プロセススキルが進め方を決め、その後に実装スキル（frontend-design など）がそれを実行します。brainstorming と systematic-debugging は Superpowers で最もよく使われるプロセススキルですが、このルールはどのプロセススキルにも当てはまります。

- 「X を作ろう」→ まず superpowers:brainstorming、次に実装スキル。
- 「このバグを直して」→ まず superpowers:systematic-debugging、次にドメインスキル。

## 危険信号

次のように考えたら**止まってください**。自己正当化しています:

| 考え | 現実 |
|------|------|
| 「これは単純な質問にすぎない」 | 質問もタスクです。スキルを確認してください。 |
| 「まずもっと文脈が必要だ」 | スキルの確認は、確認のための質問より**前**に行います。 |
| 「まずコードベースを探索しよう」 | **どう**探索するかはスキルが教えてくれます。先に確認してください。 |
| 「git やファイルならすぐ確認できる」 | ファイルには会話の文脈がありません。スキルを確認してください。 |
| 「まず情報を集めよう」 | **どう**情報を集めるかはスキルが教えてくれます。 |
| 「これに正式なスキルは要らない」 | スキルが存在するなら、使ってください。 |
| 「このスキルは覚えている」 | スキルは進化します。現在の版を読んでください。 |
| 「これはタスクのうちに入らない」 | 行動 = タスクです。スキルを確認してください。 |
| 「このスキルは大げさだ」 | 単純なことも複雑になります。使ってください。 |
| 「先にこれだけやっておこう」 | 何かをする**前**に確認してください。 |
| 「生産的に進んでいる気がする」 | 規律のない行動は時間を無駄にします。スキルはそれを防ぎます。 |
| 「それが何を意味するかは知っている」 | 概念を知っていること ≠ スキルを使うこと。呼び出してください。 |

## ユーザーの指示

ユーザーの指示（CLAUDE.md、AGENTS.md、GEMINI.md など、および直接の依頼）はスキルより優先され、スキルはデフォルトの振る舞いより優先されます。スキルのワークフローや指示を省略してよいのは、人間のパートナーが明示的にそう指示したときだけです。
