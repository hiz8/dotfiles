# tidying スキル 設計

## 意図

Kent Beck『Tidy First?』の考え方にならい、コードの整理（Tidying）をエージェントに
行わせるスキルを作る。中心となる原則は「構造の変更と振る舞いの変更を分ける」こと。
整理は振る舞いを変えず、小さな単位で行い、振る舞いの変更とは別のコミット・PR にする。

将来は `plugins/superpowers` を obra/superpowers への追従から切り離してカスタマイズしていく
方針であり、このスキルも最終的にはそこへ合流させる。そのため、書き方は superpowers の
スキルに合わせる。

## ゴール / 非ゴール / アンチゴール

- ゴール（ユーザー決定）
  - 場面 1: 機能追加やバグ修正の前に、これから手を加えるファイルを整理する。
    整理だけの PR にし、続く機能追加やバグ修正と混ぜない
  - 場面 2: 通常開発の合間などに、整理だけを頼まれて行う
- 非ゴール
  - 本にある「後で整理する（Tidy After）」と「整理しない」の判断
  - エージェントが自分の判断でこのスキルを使い始めること（ユーザー決定: 頼まれたときだけ）
  - brainstorming / writing-plans など既存の流れへの組み込み
  - `plugins/superpowers` と `docs/superpowers/skills-guide.md` の変更（合流は別作業）
- アンチゴール
  - 整理のつもりで振る舞いが変わる（バグ修正や「ついでの改善」が混ざる場合を含む）
  - 整理が膨らみ、レビューしにくい大きな差分になる
  - push や PR 作成をユーザーの確認なしに行う
  - 本の文章をそのまま写す（カタログは要点を自分の言葉で書く）

## 制約

- 置き場所は `claude/.claude/skills/tidying/`（ユーザー決定）。`~/.claude/skills/` は
  スキルごとの symlink になっているので、追加後に claude パッケージを stow し直して
  `~/.claude/skills/tidying` のリンクを作る
- superpowers の書き方に合わせる: frontmatter の `description` は「〜ときに使います」の形で
  使う条件だけを書く、本文は敬体、他スキルの参照は `superpowers:<スキル名>` 形式、
  「鉄則」「Red Flags」などの節立て
- 「〜が効く」「〜が効かない」系の表現を使わない
- スキル作成は `superpowers:writing-skills` に従う（ベースラインのテストを先に行う）

## 検討したアプローチ

1. **`SKILL.md` 1 ファイルにすべて入れる**
   シンプルだが、パターンごとに例を付けると長くなり、呼び出すたびに全部を読み込む。
2. **`SKILL.md`（手順と規律）＋ `tidyings.md`（パターンのカタログ）に分ける（採用）**
   `test-driven-development` が `writing-good-tests.md` を分けているのと同じ構成で、
   合流時にそのまま移せる。本文が短く、規律の部分が読み飛ばされにくい。
3. 場面ごとに 2 つのスキルに分ける
   規律の部分が重複するため外した。

ユーザーが 2 を選択。

## 決定事項

### ファイル構成

```
claude/.claude/skills/tidying/
├── SKILL.md      # 使う場面ごとの手順、鉄則、Red Flags、よくある誤り
└── tidyings.md   # 整理パターンのカタログ（使う場面・手順・短い例）
```

### description（私の判断）

ユーザーが整理を依頼したことをトリガーにする（例:「整理して」「tidy」「Tidy First」
「この変更の前にファイルを整えて」）。using-superpowers の「少しでも当てはまれば呼び出す」
ルールがあるため、「機能追加の前」のような状況をトリガーにすると、頼まれていないのに
使い始めてしまう。手順の要約は書かない。

### SKILL.md の中身（私の判断）

- **鉄則:** 整理のコミットに振る舞いの変更を入れない。1 つの整理ごとにテストを通して
  コミットする
- **共通の手順:**
  1. 対象を決める（場面 1 はこれから手を加えるファイル、場面 2 は依頼された範囲）
  2. テストを実行してグリーンであることを確かめる
  3. 整理の候補を `tidyings.md` から選び、一覧にしてユーザーに見せる
  4. 候補ごとに「適用 → テスト → コミット」を繰り返す
  5. 結果と、見つけた問題（下記）を報告する
- **場面 1 のブランチと PR:** 整理用のブランチで作業し、続く機能追加やバグ修正は
  その後に別のブランチで行う（整理ブランチから切るか、マージ後に切るかはユーザーに確認）。
  仕上げは `superpowers:finishing-a-development-branch` に委ね、push や PR 作成は
  スキル自身では行わない
- **場面 2 の範囲と止めどき:** 依頼された範囲から外へ広げない。候補の一覧を消化したら
  止める。差分が大きくなりそうなら、一覧の時点で分割を提案する
- **整理中に見つけたバグや改善点:** その場で直さず、記録して最後に報告する
- **テストがないとき（ユーザー決定）:** 整理の前に、現在の振る舞いを固定するテスト
  （characterization test）を別のコミットで追加し、グリーンを確かめてから整理を始める。
  「読めば振る舞いが変わらないと分かる整理だけに絞る」案は採らない
- **完了の確認:** `superpowers:verification-before-completion` に従う
- **コミット:** プロジェクトのコミット規約に従う（このリポジトリでは `commit` スキル、
  種別は `refactor`）

### tidyings.md の中身（私の判断）

本で扱う整理パターン（Guard Clause、Dead Code の削除、対称性をそろえる、
新しいインターフェースと古い実装、読む順、凝集の順、宣言と初期化を近づける、
説明用の変数・定数、明示的な引数、文のまとまり、ヘルパーの抽出、いったん 1 か所にまとめる、
説明用のコメント、冗長なコメントの削除）を、各パターンごとに「使う場面」「手順」
「短い例」で書く。例の言語は 1 つにそろえる（TypeScript）。

### テスト（writing-skills に従う。私の判断）

スキルなしで subagent に以下のシナリオを実行させ（RED）、失敗が出た項目だけを
スキルに書く。対照で失敗が出なかった項目は書かない。

1. 整理中にバグを見つける（その場で直したくなる）
2. 対象ファイルにテストがない
3. 空き時間の整理で範囲が広がる
4. 複数の整理を 1 コミットにまとめる

スキルを入れた状態で同じシナリオを実行し（GREEN）、新しい自己正当化があれば塞ぐ（REFACTOR）。

## 実装者に残すこと

- `tidyings.md` の各パターンの具体的な例
- Red Flags と自己正当化の表の中身（RED の結果から作る）
