# commit スキルのリポジトリ別拡張 設計

## 意図と背景

- u-motion-front では、subject の先頭に `[機能名]` 形式のラベルを付ける慣習がある
  （例: `[個体詳細画面][モバイル] 検索機能を修正`）。共通の commit スキルは `feat:` 形式の
  種別を前提にしているため、u-motion-front 用に iji-commit というコピーを別途保守している。
- 一番の目的は、この iji-commit のコピーを保守し続けるのを止めること。接頭辞だけは
  リポジトリの慣習に従い、それ以外（本文の書き方、表示幅、subagent への委譲、`-F` での
  コミットなど）はユーザー個人の共通ルールをそのまま使いたい。
- 共通スキル（dotfiles の `claude/.claude/skills/commit/`）は仕事用以外のプライベート開発でも
  広く使う。u-motion-front 固有の内容は共通スキルに持ち込まず、拡張できる仕組みだけを持たせ、
  拡張の中身は u-motion-front 側に置く。

## ゴール

- リポジトリ側に置いた拡張ファイルで、subject の接頭辞の形式と、その選び方の規約を
  差し替えられるようにする。
- 拡張がないリポジトリでは、今と完全に同じ挙動（`feat:` 系の種別）になる。
- u-motion-front のどの worktree からでも、同じ拡張が使われる。

## 非ゴール

- 本文のルール（表示幅、早すぎる改行、装飾、Co-Authored-By など）の拡張。本文は常に共通の
  判定を使う。
- タイトル長（50 文字）の上限値の変更。緩和は共通スキルそのものの仕様変更なので、
  この設計とは別の変更で扱う。
- 拡張ファイルを team のリポジトリにコミットして共有すること（個人用として置く）。
- iji-commit の削除作業そのもの（u-motion-front 側の個人作業で、この計画の範囲外）。

## アンチゴール（動いても失敗とみなすもの）

- u-motion-front で、拡張が見つからないまま黙って `feat:` 形式でコミットしてしまうこと。
  どちらの規約を使ったかを必ずサマリに出し、ユーザーがコミット直後に気付けるようにする。
- 共通スキルに u-motion-front の名前・ページ名・ラベルの知識が入ること。
- 拡張の設定が壊れている（JSON や正規表現の誤り）ときに、黙って共通規約に戻ること。

## 制約

- 拡張ファイルは個人用で、u-motion-front では `.git/info/exclude` によって git 管理外にする。
- git 管理外のファイルは worktree に入らない。u-motion-front の worktree は
  `~/work/u-motion/u-motion-front.worktrees/` や `~/.windsurf/worktrees/` に作られ、作成フック
  （`.claude/worktree-hooks/create.js`）がコピーするのも `gulp/setup.js` だけ。
- 検証ツールは Node 標準ライブラリだけで動かす（今と同じ）。テストは `node:test` を使い、
  ファイルパスを指定して実行する（`node --test <dir>` は失敗するため）。
- 共通スキルの文書は今の敬体・規範表現（「〜してはいけません」など）に合わせる。

## 検討した方式

- A. 共通スキルに u-motion-front 用のラベル規約を組み込み、リポジトリ名などで切り替える。
  - 実装は最小だが、共通スキルに u-motion-front 固有の知識が入る。プライベート開発でも使う
    共通スキルを汚すため不採用。
- B. 共通スキルには汎用の拡張点だけを持たせ、接頭辞の定義と接頭辞ガイドをリポジトリ側に置く。
  - 共通スキルはどのリポジトリの事情も知らずに済む。拡張の発見方法を worktree でも動くように
    設計する必要がある。**ユーザーが選択。**
- C. リポジトリ側に共通スキルを包むラッパースキル（iji-commit の薄い版）を置く。
  - 手順書や本文の規約がまた二重になり、コピー保守をやめる目的に反するため不採用。

## 決まった設計

用語: 接頭辞ガイドは、subject の接頭辞（u-motion-front ではラベル）の選び方を書いた
Markdown。ユーザーが「ルールブック」と呼んでいたもの。

### 拡張ファイルの置き場所と発見

- 拡張ディレクトリは `<作業ツリーのルート>/.claude/commit/`。
- 探す順序（最初に見つかったものを使う。設計者の判断）。
  1. 今いる作業ツリーのルート（`git rev-parse --show-toplevel`）
  2. メインの作業ツリーのルート（`git rev-parse --git-common-dir` から求める）
- メインの作業ツリーに 1 か所置けば、どの worktree からでも使える。メインの作業ツリーで
  作業している場合は 1 と 2 が同じ場所になる。
- git リポジトリの外、または拡張ディレクトリが見つからない場合は、共通規約で判定する。

### 拡張ファイルの中身（u-motion-front 側に置く）

- `config.json`
  - 接頭辞の正規表現。subject の先頭に一致する必要がある。
    例: `^(\[[^\[\]]+\])+ `
  - 違反したときの説明文と、正しい subject の例。
  - 接頭辞ガイドのファイル名。
- 接頭辞ガイド（Markdown）
  - ページ一覧の表と、ラベルの選び方を書く。
  - 共通規約（`commit-rules.md`）の「コミット種別」節の代わりに読まれる。それ以外の節は
    共通規約のまま。
  - u-motion-front では次の規約を書く（中身は u-motion-front 側でユーザーが管理する）。
    - 複数画面にまたがる「特定機能の実装」は、ユーザーがラベルを明示する。
    - それ以外は、ページ一覧の表にあるページ名をラベルにする。
    - `Jest:`、`Panda CSS:`、`Prettier` のような横断的な種別や、`feat:` 系の種別は使わない。
      正規表現で不合格にする。

### 共通スキル側の変更（汎用の仕組みだけ）

- 検証ツール（`check-commit-message.mjs` と `lib/commit-message.mjs`）
  - 拡張があれば、種別の判定を拡張の正規表現で行う。違反時は拡張の説明文と例を出す。
  - タイトル長は、拡張の正規表現に一致した接頭辞と末尾の Issue 番号を除いた残りで数える。
  - 拡張がなければ、今の `feat:` 系で判定する。
  - 本文の判定は常に共通。
  - 拡張の設定が読めない・壊れている場合（拡張ディレクトリはあるが `config.json` や
    接頭辞ガイドがない場合を含む）は、共通規約に戻らずエラーで止める（設計者の判断）。
- 手順書（`commit-procedure.md`）
  - 拡張があれば、共通規約の「コミット種別」節の代わりに接頭辞ガイドを読む。
  - ラベルが決められない場合（複数画面の機能でユーザーの指定がないなど）は、自己判断で
    コミットせず、候補を返して止まる。
- 呼び出し元へ返すサマリ
  - どちらの規約を使ったか（共通規約か、どこの拡張か）を 1 行で出す。worktree で取り違えて
    いないかをユーザーが確認できるようにするため。

### 拡張が見つからないときの扱い（ユーザーが決定）

- コミットの前に止める仕組み（「拡張が必須」の宣言など）は足さない。サマリの 1 行で
  コミット後に気付ければ十分とする（方式 (a)）。
  - 理由: worktree からはメインの作業ツリーの拡張が見つかる。見つからないのは、別に clone
    した場合と、拡張を置く前の時期だけで、どちらもまれ。使うのはユーザー 1 人で、間違えたら
    amend で直せる。

### 移行

- 共通スキル側の変更が入った後、ユーザーが u-motion-front のメインの作業ツリーに
  `.claude/commit/` を置き、iji-commit を削除する（`.claude` は既に `.git/info/exclude` 済み）。

## ビルダーに任せること

- `config.json` のキー名と、接頭辞ガイドのファイル名の既定値（例: `prefix-guide.md`）。
- 拡張ディレクトリのパスを手順書（subagent）がどう知るか（検証ツールに表示用の
  オプションを足す、など）。
- 正規表現が `^` で始まらない場合の扱い（先頭一致に揃える方法）。
- テストで一時的な git リポジトリと worktree をどう作るか。
