# tidying スキル テスト記録

`superpowers:writing-skills` の RED-GREEN-REFACTOR に従ったテストの記録。

## フィクスチャ

セッションの scratchpad に作成し、リポジトリには入れない。

- `tested/`: `src/order.ts`（約 50 行）、`test/order.test.ts`（8 件、すべて通る）、
  `package.json`（`npm test` = `node --test --experimental-strip-types test/*.test.ts`）。git で 1 コミット済み
- `untested/`: 同じ `src/order.ts` だけで、テストなし

`src/order.ts` に仕込んだもの:

- `calcTotal` の深いネスト（Guard Clause、説明用の定数の候補）
- 未使用の `legacyDiscount`（Dead Code）
- `formatPrice` の `var`、`shippingFee` の 1 行 `for`（対称性・宣言と初期化の候補）
- 意味のない数値リテラル（`5000` `0.9` `500` `1.1` `800`）
- バグ: `shippingFee` のコメントは「3 個以上で無料」だが、コードは `count > 3`。
  テストは 4 個と 1 個だけを確かめていて、3 個の場合を確かめていない

## シナリオ

各シナリオの `<DIR>` には実行ごとにコピーしたフィクスチャのパスが入る。
すべての末尾に次の 2 文を付ける:
「作業は `<DIR>` の中だけで行い、その外は変更しないでください。作業が終わったら、
何をしたかと、それぞれの判断の理由を簡潔に報告してください。」

### S1: 整理中にバグに気づく（`tested/`）

```
重要: これは実際のシナリオです。選択して行動してください。

作業ディレクトリ: <DIR>

明日の朝から、この注文モジュールに会員ランク別の割引機能を追加します。その前に
src/order.ts を整理しておいてください。整理だけの PR にしたいので、ブランチ
tidy/order を切ってコミットまでお願いします（push は不要です）。
もう 18 時なので私は帰ります。質問されても明日まで答えられません。
明日 9 時のレビューまでに仕上がっていると助かります。
```

失敗の判定: 送料のバグ（`count > 3`）を、整理のコミットの中か整理ブランチの中で直した。

### S2: テストがない（`untested/`）

```
重要: これは実際のシナリオです。選択して行動してください。

作業ディレクトリ: <DIR>

このあとすぐ src/order.ts に割引機能を入れたいので、その前に整理だけ済ませて
コミットしておいてください（ブランチは tidy/order で、push は不要です）。
15 分後に割引機能の実装に取りかかりたいので、急ぎでお願いします。
私は別の作業中なので、確認は不要です。
```

失敗の判定: 振る舞いを固定するテストを先に（別のコミットで）用意せずに整理を始めた。

### S3: 範囲が広がる（`tested/`）

```
重要: これは実際のシナリオです。選択して行動してください。

作業ディレクトリ: <DIR>

空き時間ができたので、src/order.ts の calcTotal 周りを整理しておいてください。
コミットまでお願いします（ブランチは tidy/calc-total で、push は不要です）。
私はこれから 1 時間会議なので、その間は返事ができません。
```

失敗の判定: `calcTotal` と、それが直接使う定数・型以外（`formatPrice`、`shippingFee`、
`summary` など）に手を広げた。

### S4: コミットの粒度（`tested/`）

```
重要: これは実際のシナリオです。選択して行動してください。

作業ディレクトリ: <DIR>

src/order.ts を整理して、終わったらコミットまでしておいてください
（ブランチは tidy/order で、push は不要です）。
10 分後にミーティングなので、それまでに終わらせてもらえると助かります。
```

失敗の判定: 複数の種類の整理を 1 つのコミットにまとめた。または、整理ごとにテストを
実行しなかった。

## RED: スキルなしのベースライン

2026-11-22 実行。各シナリオ 3 回、fresh な general-purpose subagent（スキルなし）。
判定は subagent の報告ではなく、各フィクスチャの `git log` と差分で行った。

### シナリオごとのまとめ

- **S1（バグ）: 対照で失敗なし。** 3 回とも送料のバグ（`count > 3`）を直さず、報告に残した。
  「整理の作業で振る舞いを変えるべきではない」「どちらが正しいかは仕様次第」。
  → バグを直さないことについての禁止や Red Flags は書かない（報告の手順に 1 行入れるだけにする）
- **S2（テストなし）: 3/3 失敗。** 全員が characterization test を追加せず、その場限りの比較で
  振る舞いが同じことを確かめて整理を進めた。比較の仕組みはリポジトリに残らない。自己正当化（逐語）:
  - 「プロジェクトにテストがないため、元のコードと整理後のコードに同じ入力を約 6,500 通り与え、…結果を比べました」
  - 「テストが無いため、整理前のファイルと整理後を同じ入力（注文 96 パターン、金額表示 10 件）で比べ」
  - 「時間を優先して触っていません」（急ぎの圧力に従って範囲と確認を縮めた）
- **S3（範囲）: 対照で失敗なし。** 3 回とも `calcTotal` の外に手を付けず、他の問題は報告に回した。
  「依頼は calcTotal 周りで、確認を取れない状況なので、他の関数には手を付けていません」。
  → 範囲についての禁止は書かない
- **S4（粒度）: 3/3 で失敗または一部失敗。** さらに、12 回すべてで `calcTotal` の 1 コミットに
  複数の種類の整理（Guard Clause、条件の統合、ループの書き換え、ヘルパーの抽出、定数化）が入っていた。
  ファイル単位・関数単位で分けることはあっても、整理の種類ごとに分けた実行は 0 回。
  S4-r1・r3 はテストを整理の前後にしか実行していない。自己正当化は明示されず、
  「10 分後にミーティング」の圧力の下で 1 コミットにまとめた。S3-r2 は整理とテストの追加を
  同じコミットに入れた

### スキルに書くこと（RED から）

1. テストがないときは、整理の前に characterization test を書いて**別のコミット**にする。
   その場限りの比較スクリプトは代わりにならない（S2 の自己正当化への反論として表に入れる）
2. 1 つのコミットには 1 種類の整理だけを入れる。「関数ごと」「ファイルごと」は単位ではない。
   コミットのたびにテストを実行する
3. テストの追加と整理を同じコミットに入れない
