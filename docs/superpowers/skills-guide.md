# superpowers スキルガイド

## 全体の流れ

新しい機能を作るときは、スキルが次の順に引き継がれていきます。

```
brainstorming          … 何を作るかを固め、設計ドキュメントの承認を得る
  ↓
writing-plans          … 設計をタスク単位の実装計画書にする
  ↓
using-git-worktrees    … 隔離されたワークスペースを用意する
  ↓
subagent-driven-development（推奨） または executing-plans
  │                    … 計画書をタスクごとに実装する
  ├─ test-driven-development         各タスクを RED-GREEN で進める
  ├─ systematic-debugging            想定外の失敗が出たら根本原因を探す
  ├─ verification-before-completion  「完了」と言う前に証拠を確かめる
  └─ requesting-code-review          タスクごと／ブランチ全体をレビューする
  ↓
finishing-a-development-branch … マージ・PR・保留のどれにするかを決める
```

バグ修正は systematic-debugging から始めます。レビューの指摘を受けたときは
receiving-code-review を使います。

## 早見表

| 分類 | スキル | 使う場面 |
|------|--------|----------|
| 設計・計画 | brainstorming | 機能の追加や振る舞いの変更など、何かを新しく作る前 |
| 設計・計画 | writing-plans | 仕様や設計があり、コードに触れる前 |
| 実行 | subagent-driven-development | 計画書を、タスクごとに subagent へ任せて実行するとき |
| 実行 | executing-plans | 計画書を、自分自身でまとめて実行するとき |
| 実行 | using-git-worktrees | 現在のブランチを汚さずに作業を始めるとき |
| 品質・規律 | test-driven-development | 機能の実装やバグ修正で、実装コードを書く前 |
| 品質・規律 | systematic-debugging | バグ、テストの失敗、想定外の振る舞いに出会ったとき |
| 品質・規律 | verification-before-completion | 「完了」「直った」「テストが通る」と言う前、コミットや PR の前 |
| レビュー | requesting-code-review | タスクや主要な機能が完成したとき、マージの前 |
| レビュー | receiving-code-review | レビューの指摘を受け、対応する前 |
| 仕上げ | finishing-a-development-branch | 実装が終わってテストが通り、統合のしかたを決めるとき |
| メタ | using-superpowers | 会話の開始時（自動で読み込まれます） |
| メタ | writing-skills | スキルを作成・編集・検証するとき |

スキルは状況に応じて自動で呼び出されます。`/superpowers:<スキル名>` で明示的に
呼び出すこともできます。

## 設計・計画

### brainstorming

- **概要:** 作り始める前に、相手が本当に何を望んでいるのか、なぜそれを望むのかを
  対話で明らかにし、設計ドキュメントにまとめます
- **使う場面:** 機能の作成、振る舞いの変更、新しいことの計画など、創造的な作業の前。
  ソフトウェア以外（講演、事業など）にも使えます
- **要点:**
  - 質問は 1 つずつ、答え次第で作るものが変わる点に絞ります。質問の前にコードや資料を調べます
  - 作り方の候補を 2〜3 案並べ、推奨を添えて選んでもらいます
  - 作業の規模に応じて、短い設計か完全な設計を `docs/superpowers/specs/` に書きます。
    完全な設計では、subagent に「ビルダーチェック」をさせて抜けを洗い出します
  - **設計ドキュメントが承認されるまで、何も作りません**（使い捨ての試作は例外）
  - 画面やレイアウトを見せたほうが分かりやすい場面では、モックアップを表示する
    ブラウザタブ（ビジュアルコンパニオン）を提案します
- **つながり:** 承認後は writing-plans へ進みます

### writing-plans

- **概要:** コードベースを知らない実装者でも迷わないよう、実装計画書を書きます
- **使う場面:** 複数ステップのタスクの仕様や要件があり、コードに触れる前
- **要点:**
  - 保存先は `docs/superpowers/plans/YYYY-MM-DD-<機能名>.md` です
  - 先にファイル構成と各ファイルの責務を決め、それに沿ってタスクを分けます
  - 各タスクには対象ファイル、Interfaces（前後のタスクとの受け渡し）、
    「失敗するテスト → 失敗を確認 → 実装 → 通ることを確認 → コミット」のステップを書きます
  - 冒頭に Global Constraints と、テストで見落としやすい失敗モードを並べた
    Review Focus を置きます
  - 書き終えたら仕様と突き合わせてセルフレビューし、実行方法を選んでもらいます
- **つながり:** brainstorming の後に使います。実行は subagent-driven-development
  または executing-plans に引き継ぎます

## 実行

### subagent-driven-development

- **概要:** タスクごとに新しい実装者 subagent を立て、各タスクの後にレビュー
  （仕様準拠とコード品質）を行い、最後にブランチ全体をレビューします
- **使う場面:** おおむね独立したタスクからなる計画書を実行するとき。
  タスクごとにレビューを挟みたい場合や、長い計画書に向いています
- **要点:**
  - タスクの合間に確認のために止まりません。曖昧な点は自分で裁定し、
    `Ruling:` として ledger に記録して進みます
  - 止まって尋ねるのは、不可逆・破壊的な操作、セキュリティに関わる操作、
    マージや共有ブランチへの push など外部への副作用、当て推量になるほど壊れた計画書の 4 つだけです
  - 進捗は `.superpowers/sdd/` 配下の ledger に記録し、コンテキスト圧縮後も再開できるようにします
  - subagent には役割に見合ったモデルを明示的に指定します（機械的な実装には安価なモデル、
    最終レビューには最も高性能なモデル）
- **つながり:** using-git-worktrees でワークスペースを用意して始め、
  finishing-a-development-branch で終えます

### executing-plans

- **概要:** 計画書を、このセッションで自分自身がタスクごとに実装します。
  最後にブランチ全体を新しいコンテキストで 1 回レビューします
- **使う場面:** インライン実行を選んだとき、または subagent ツールがないとき
- **要点:**
  - subagent-driven-development より安価で速い代わりに、タスクごとの独立したレビューはありません
  - 開始前に test-driven-development を読み込み、すべてのステップをその規律で進めます
  - 連続実行、裁定の記録、止まる 4 条件は subagent-driven-development と同じです
  - ワークスペースと ledger の形式も共通なので、途中で実行方法を切り替えられます
- **つながり:** using-git-worktrees で始め、finishing-a-development-branch で終えます

### using-git-worktrees

- **概要:** 作業を、現在のブランチから隔離されたワークスペースで行えるようにします
- **使う場面:** 機能開発を始めるとき、計画書を実行する前
- **要点:**
  - まず、すでに worktree の中にいるかを確かめ、いれば新たに作りません
  - 実行環境のネイティブな worktree 機能を優先し、ない場合だけ `git worktree` を使います
  - 置き場所は既存の `.worktrees/` または `worktrees/`、なければ `.worktrees/` を使い、
    `.gitignore` に入っているかを確認します
  - 作成後に依存関係をインストールし、テストが通るクリーンな状態であることを確認します
- **つながり:** 実行スキル（subagent-driven-development / executing-plans）の準備として使います

## 品質・規律

### test-driven-development

- **概要:** 先にテストを書き、失敗を確認してから、通す最小限のコードを書きます
- **使う場面:** 新機能、バグ修正、リファクタリング、振る舞いの変更のすべて。
  使い捨ての試作、生成コード、設定ファイルは相手に確認して例外にできます
- **要点:**
  - 鉄則は「失敗するテストが先にない限り、プロダクションコードを書かない」です
  - テストより先に書いたコードは、参考にも残さず削除してやり直します
  - RED（失敗するテスト）→ GREEN（最小限のコード）→ REFACTOR（整理）を繰り返します
  - 失敗するのを見ていないテストは、正しいものをテストしているか分かりません
- **つながり:** 実行スキルの各タスク、systematic-debugging の修正段階で使います

### systematic-debugging

- **概要:** 修正を試す前に、必ず根本原因を突き止めます
- **使う場面:** テストの失敗、本番のバグ、想定外の振る舞い、性能の問題、
  ビルドの失敗など、あらゆる技術的な問題。急いでいるときや単純に見えるときも省きません
- **要点:**
  - 4 つのフェーズを順に完了させます
    1. 根本原因の調査（エラーを読む、再現する、変更を確認する、証拠を集める）
    2. パターン分析（動作する例と比べて違いを特定する）
    3. 仮説とテスト（仮説を立て、最小限の変更で確かめる）
    4. 実装（失敗するテストを作り、修正を 1 つだけ入れて検証する）
  - 3 回以上修正に失敗したら、修正を重ねずにアーキテクチャを疑います
  - 原因の遡り方、多層での検証、条件待ちといった補助手法の資料が付いています
- **つながり:** 修正では test-driven-development を、完了の主張では
  verification-before-completion を使います

### verification-before-completion

- **概要:** 完了を主張する前に、検証コマンドを実行して出力を確かめます
- **使う場面:** 「完了した」「直った」「テストが通る」と言う前、コミットや PR を作る前
- **要点:**
  - 鉄則は「新しい検証の証拠がない限り、完了を主張しない」です
  - 主張を裏付けるコマンドを特定し、全体を実行し、出力と終了コードを読み、
    裏付けられた場合だけ主張します
  - 以前の実行結果、「通るはず」、subagent の成功報告は証拠になりません
  - 「はず」「おそらく」と言いかけたら、止まって検証します
- **つながり:** 実行スキルやデバッグの締めくくりで使います

## レビュー

### requesting-code-review

- **概要:** コードレビュアー subagent に、評価に必要な文脈だけを渡してレビューさせます
- **使う場面:** subagent-driven-development の各タスクの後、主要な機能の完成後、
  マージの前（必須）。行き詰まったとき、リファクタリングの前、複雑なバグの修正後にも役立ちます
- **要点:**
  - レビュー範囲を BASE と HEAD の git SHA で示し、テンプレートに要件と要約を埋めて渡します
  - セッションの履歴は渡しません
  - 指摘は Critical はすぐ、Important は先に進む前に直し、Minor は記録しておきます。
    レビュアーが誤っていれば根拠を添えて反論します
- **つながり:** 指摘を受けた後は receiving-code-review の姿勢で対応します

### receiving-code-review

- **概要:** レビューの指摘に、見せかけの同意ではなく技術的な検証で応えます
- **使う場面:** レビューの指摘を受けて、実装する前。特に、指摘が不明確だったり
  技術的に疑わしかったりするとき
- **要点:**
  - 読む → 自分の言葉で言い直す → コードベースと照らす → 妥当か評価する →
    了承または根拠ある反論 → 1 項目ずつ実装してテスト、の順で進めます
  - 「おっしゃる通りです!」「いい指摘ですね!」のような演技的な応答はしません
  - 人間のパートナーからの指摘は信頼して実装します。外部レビュアーの指摘は、
    このコードベースで正しいかを確かめてから実装します
  - 「本格的な」実装を求める指摘には、本当に必要かを確かめます（YAGNI）
- **つながり:** requesting-code-review の後に使います

## 仕上げ

### finishing-a-development-branch

- **概要:** 実装が終わったブランチを、どう統合するか決めて実行し、後片付けまで行います
- **使う場面:** 実装が完了し、すべてのテストが通ったとき
- **要点:**
  - テストを検証 → 環境を検出 → ベースブランチを特定 → 選択肢を提示 → 実行 → 後片付け、の順です
  - 選択肢は「ローカルでマージ」「push して PR を作成」「ブランチをそのまま残す」の 3 つです
    （detached HEAD のときは 2 つ）
  - 統合の判断は人間のパートナーのものです。作業の破棄は明示的に頼まれたときだけ行います
- **つながり:** 実行スキルの最後に使います

## メタ

### using-superpowers

- **概要:** スキルの見つけ方と使い方を定めます
- **使う場面:** あらゆる会話の開始時。セッション開始時のフックで自動的に読み込まれます
- **要点:**
  - 関連しそうなスキルは、確認の質問やファイルの確認も含め、どんな応答や行動よりも先に呼び出します
  - 複数が当てはまるときは、進め方を決めるプロセススキル（brainstorming、
    systematic-debugging など）を先に使います
  - plan mode に入る前に、まだなら brainstorming を使います
  - 指示ファイルや直接の依頼は、スキルより優先されます

### writing-skills

- **概要:** スキルの作成を、ドキュメントに対する TDD として進めます
- **使う場面:** 新しいスキルの作成、既存スキルの編集、スキルが機能するかの検証
- **要点:**
  - スキルなしで subagent に圧力のかかるシナリオを解かせ、ルール違反と
    その自己正当化を記録します（RED）
  - その違反に対処するスキルを書き、従うようになったことを確かめます（GREEN）
  - 新たな抜け穴を見つけてふさぎ、再検証します（REFACTOR）
  - 一度きりの解決策、プロジェクト固有の規約、機械的に強制できる制約はスキルにしません
- **つながり:** test-driven-development の考え方を前提にします
